# CADI Assist

**AI-powered conversational assistant for the CADI website at the University of Portsmouth**

A self-contained, single-file chat interface that uses Claude (Anthropic's AI) to answer natural language questions from staff about CADI services, CPD, fellowship pathways, assessment, and learning design. The assistant draws on a knowledge base built from the live CADI website, which is automatically refreshed weekly by a GitHub Actions crawler.

## 1. How it works

The system has four moving parts that work together:

```
Staff member types a question
        ↓
index.html (browser)
  — fetches search-index.json from GitHub (live page data)
  — scores the index against the query + recent conversation context
  — sends the top 20 most relevant pages + conversation history to Cloudflare Worker
        ↓
Cloudflare Worker (API proxy)
  — holds the Anthropic API key securely
  — forwards the request to Claude
        ↓
Claude (claude-sonnet-4-20250514)
  — reads the focused knowledge base and full conversation history
  — answers conversationally, linking to relevant pages inline
  — if no relevant pages were found, says so clearly and directs staff to the team
        ↓
index.html renders the response as a chat message
```

Separately, a GitHub Actions workflow runs every Sunday at 2am UTC. It executes `scripts/crawl.py` against `https://cadi.port.ac.uk`, produces a fresh `search-index.json`, and commits it back to the repository. The next time a user opens the assistant, their browser fetches this updated knowledge base automatically.

**No backend server is required.** The only server-side component is the lightweight Cloudflare Worker, which exists solely to keep the Anthropic API key out of the browser.

### Key difference from the search version

The search interface sends a query to Claude and asks it to return a ranked JSON list of page IDs. The assistant instead scores the index locally, then passes the most relevant pages as a system-level context and lets Claude answer conversationally in plain English, linking to relevant CADI pages inline using markdown. This means:

- Staff get direct answers rather than a list of links to click through
- Follow-up questions are supported — the full conversation history is sent with every message, and scoring uses recent conversation context so Claude stays on topic
- Claude can synthesise information across multiple pages in a single response
- The response format is natural prose, not structured JSON

## 3. The chat interface (index.html)

The entire frontend is a single HTML file. It uses React (loaded from a CDN) with Babel for JSX transpilation in-browser, meaning no build step, no Node.js, and no npm are needed. You can open the file directly in a browser for development, though the assistant will not connect until a valid `PROXY_URL` is set.

### Key sections inside index.html

**`CONFIGURATION`** (top of the `<script>` block) — the two values you must set before deploying:

```js
const PROXY_URL = "https://cadi-search-proxy.kristian-band.workers.dev";
const GITHUB_RAW_INDEX_URL = "https://raw.githubusercontent.com/.../search-index.json";
```

**`FALLBACK_INDEX`** — a small hardcoded array of the most important CADI pages, used if the live `search-index.json` cannot be fetched (e.g. a network issue or the GitHub URL is not yet configured). This is a safety net, not the primary knowledge source. Keep it reasonably current with the most important pages.

**`EXAMPLE_PROMPTS`** — the suggestion chips shown on the welcome screen before any message is sent. Update these to reflect the questions staff most commonly ask. Review GA search data periodically to inform this.

### How a conversation turn works (step by step)

1. The user types a message and presses Enter or clicks the send button.
2. The browser fetches `search-index.json` from GitHub on first load and holds it in memory.
3. On each message, the browser scores the full index against the user's query (see [Relevance scoring](#relevance-scoring) below) and selects the top 20 pages.
4. The browser POSTs to the Cloudflare Worker with a JSON body containing:
   - The Claude model name
   - A system prompt containing only the top 20 scored pages as the knowledge base
   - The complete conversation history (all previous messages in the session)
   - The new user message
5. The Worker adds the `x-api-key` header and forwards the request to `api.anthropic.com/v1/messages`.
6. Claude reads the knowledge base and conversation history, then responds in plain English, linking to relevant CADI pages using markdown `[text](url)` syntax.
7. The browser renders the response as a chat bubble, converting markdown links to clickable `<a>` tags.

### Relevance scoring

Before every API call, two functions filter the index down to the most relevant pages for the current conversation:

**`getCorePages(index)`** — detects the homepage, contact page, and about page by URL pattern (no hardcoded IDs). The homepage is identified by a path of `/` or empty; contact and about are found by `/contact` and `/about` in the URL. These three pages are always included in the knowledge base regardless of their relevance score.

**`scorePages(index, query, topN = 20)`** — scores every page against the combined query string (see below) across four fields with weighted points:

| Field | Points per matching word |
|---|---|
| Title | 10 |
| Tags | 8 |
| Tag string (multi-word tags) | 5 |
| Excerpt | 4 |
| Content (first 600 chars) | 2 |

Matching uses a fuzzy comparator that handles misspellings and partial words — for example `felowship` matches `fellowship`, and `timetab;e` matches `timetable`. Pages are sorted by descending score and the top 20 are returned. Core pages (homepage, contact, about) are appended if not already in the top 20.

`scorePages` returns `{ pages, maxScore }`. When `maxScore` is 0 — meaning no page scored any points against the query — a note is added to the system prompt instructing Claude to acknowledge that it could not find relevant information and to direct staff to the CADI team or website.

### Scoring against conversation context (Option B)

`buildSystemPrompt(index, query, priorMessages)` combines the last 3 user messages with the current message before scoring:

```js
const recentContext = priorMessages
  .filter(m => m.role === "user")
  .slice(-3)
  .map(m => m.text)
  .concat(query)
  .join(" ");
```

This means follow-up questions like "what about the timetable?" are scored with the context of the whole recent thread, not just those four words. Without this, a vague follow-up could return a completely unrelated set of pages.

### The system prompt

The system prompt is built in `buildSystemPrompt`. It:

- Identifies Claude as CADI Assist, an assistant for the University of Portsmouth
- Lists the topics Claude should help with (CPD, fellowship, peer observation, assessment, learning design, technology tools, conferences)
- Instructs Claude to answer in 2–4 short paragraphs using plain English
- Instructs Claude to include relevant page URLs as markdown links when genuinely useful
- Instructs Claude to be honest when it does not have specific details (e.g. exact session dates) and to direct staff to the CADI website or team
- Passes the filtered knowledge base inline as a `KNOWLEDGE BASE:` section
- Appends a gap note when `maxScore === 0` (see [Relevance scoring](#relevance-scoring))

Each page in the knowledge base is formatted as:

```
TITLE: CPD and Support
URL: https://cadi.port.ac.uk/cpd-support
TYPE: page
SUMMARY: The main hub for Continuing Professional Development…
DETAIL: CPD opportunities including workshops on active blended learning…
TAGS: cpd, professional development, fellowship, workshops, training
```

To change Claude's behaviour or tone, edit `buildSystemPrompt` in `index.html`.

### Conversation history

The full message history for the current session is held in the `messages` React state array and sent to Claude on every turn. This allows Claude to answer follow-up questions in context. History is cleared when the user clicks the **Clear** button or closes/refreshes the page. There is no persistent storage between sessions.

## 4. The site crawler (scripts/crawl.py)

The crawler is a Python script that performs a breadth-first crawl of the CADI website and outputs a structured JSON file used as the assistant's knowledge base.

### Running the crawler manually

```bash
# Install dependencies (Python 3.11+ recommended)
pip install requests beautifulsoup4 lxml

# Run against the live site
python scripts/crawl.py \
  --url https://cadi.port.ac.uk \
  --max-pages 300 \
  --output search-index.json
```

| Argument | Default | Description |
|---|---|---|
| `--url` | *(required)* | Root URL to start crawling from |
| `--max-pages` | `300` | Maximum number of pages to index |
| `--stay-on-domain` | `true` | If `true`, only follows links on the same domain |
| `--output` | `search-index.json` | Output file path |

### How the crawler works

1. Starts at the root URL and maintains a queue of URLs to visit.
2. Reads `robots.txt` and skips any disallowed paths.
3. For each page it fetches, it:
   - Strips navigation chrome, headers, footers, scripts, and CADI-specific noise elements (`NOISE_TAGS`)
   - Extracts the main content using a priority list of CSS selectors (`CONTENT_SELECTORS`) — tuned specifically for Drupal's HTML structure
   - Extracts supplemental content from signposts, quotes, and accordion components (`SUPPLEMENTAL_SELECTORS`)
   - Infers the content type (page, event, resource, guide) from URL patterns and Drupal body classes
   - Extracts meta tags for description, date, and tags
4. Writes a JSON file with a record per page (see [Section 5](#5-the-knowledge-index-search-indexjson)).
5. Waits 0.5 seconds between each request to be polite to the server (`CRAWL_DELAY`).

### Adapting the crawler for a different site

If the CADI Drupal site is ever restructured, the selectors may need updating:

- **`CONTENT_SELECTORS`** — ordered list of CSS selectors tried in sequence to find the main content area. If the Drupal theme changes its class names, update these.
- **`NOISE_TAGS`** — elements to strip before extracting text. Add selectors for any new persistent UI chrome (cookie banners, chat widgets, etc.).
- **`SUPPLEMENTAL_SELECTORS`** — CADI-specific components whose text should be appended to the main content even if they sit outside the primary content container.
- **`infer_content_type`** — the heuristic for deciding whether a page is a `page`, `event`, `resource`, or `guide`. Update the URL patterns and Drupal body classes to match any new content types.

## 5. The knowledge index (search-index.json)

This file is committed to the repository and served as a raw GitHub file. It is fetched by the browser on first load and held in memory for the duration of the session. The browser scores it locally on every turn and passes only the top 20 pages to Claude.

```json
{
  "generated_at": "2026-05-10T05:27:02Z",
  "source_url": "https://cadi.port.ac.uk",
  "total_pages": 181,
  "pages": [
    {
      "id": 1,
      "url": "https://cadi.port.ac.uk/cpd-support",
      "title": "CPD and Support | CADI",
      "excerpt": "First 300 characters of extracted text…",
      "content": "First 1500 characters of extracted text (used for scoring and sent to Claude)",
      "type": "page",
      "tags": ["cpd", "workshops"],
      "date": "2026-03-01",
      "description": "Meta description from the page"
    },
    ...
  ]
}
```

**Do not edit this file by hand.** It is overwritten entirely on every crawler run.

### Token usage

Because only the top 20 scored pages are passed to Claude (rather than the full index), token usage per request is approximately 3,000–5,000 tokens regardless of how large the index grows. This is a ~90% reduction compared to sending the full index, and keeps requests well within the Cloudflare Worker's limits.

For reference: a 182-page index sent in full produces approximately 42,000 input tokens. With scoring, a typical query produces approximately 3,500 input tokens.

The per-page `content` field is additionally truncated to 500 characters inside `buildSystemPrompt` to balance knowledge depth against token efficiency.

## 6. GitHub Actions (automated crawling)

The workflow file at `.github/workflows/crawl_site.yml` automates the weekly index refresh.

### Schedule

The crawler runs automatically every **Sunday at 2:00am UTC**:

```yaml
schedule:
  - cron: '0 2 * * 0'
```

### Running the crawler manually via GitHub

1. Go to the repository on GitHub
2. Click **Actions** in the top navigation
3. Select **Crawl and Index Website** from the left sidebar
4. Click **Run workflow**
5. Fill in the optional inputs or leave them at their defaults
6. Click **Run workflow** again to start

The workflow crawls the site, validates the output (fails with an error if zero pages are indexed), commits the updated `search-index.json` back to the repository, and pushes the change.

### Required GitHub permissions

The workflow uses `permissions: contents: write` to commit the index file. This is already set in the workflow YAML. For private repositories, ensure the default Actions token has write access: Settings → Actions → General → Workflow permissions → "Read and write permissions".

### What happens after the commit

Because `search-index.json` is fetched directly from GitHub's raw URL at load time, the updated knowledge base becomes live for all users the next time they open the assistant — no deployment step required.

## 7. The Cloudflare Worker (API proxy)

The Cloudflare Worker is a small JavaScript function deployed to Cloudflare's edge network. Its sole purpose is to hold the Anthropic API key and forward requests from the browser to the Anthropic API.

**The Worker code is not in this repository.** It is deployed separately and lives at:

```
https://cadi-search-proxy.kristian-band.workers.dev
```

### Why a proxy is necessary

API keys must never be exposed in client-side JavaScript — they are visible to anyone who opens DevTools. The Worker sits between the browser and Anthropic's API, adding the `x-api-key` header server-side. The browser only ever sees the Worker URL; the API key is never transmitted to the browser.

### What the Worker does

```
Browser POST → Worker → adds x-api-key → Anthropic API → response back to browser
```

### Recreating the Worker

If the Worker needs to be redeployed (e.g. the Cloudflare account changes):

```js
export default {
  async fetch(request, env) {
    if (request.method === "OPTIONS") {
      return new Response(null, {
        headers: {
          "Access-Control-Allow-Origin": "*",
          "Access-Control-Allow-Methods": "POST, OPTIONS",
          "Access-Control-Allow-Headers": "Content-Type",
        },
      });
    }

    const body = await request.text();

    const response = await fetch("https://api.anthropic.com/v1/messages", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": env.ANTHROPIC_API_KEY,
        "anthropic-version": "2023-06-01",
      },
      body,
    });

    const data = await response.text();

    return new Response(data, {
      status: response.status,
      headers: {
        "Content-Type": "application/json",
        "Access-Control-Allow-Origin": "*",
      },
    });
  },
};
```

Store the API key as a **Worker secret** named `ANTHROPIC_API_KEY`:

```bash
wrangler secret put ANTHROPIC_API_KEY
```

### API key management

The Anthropic API key is managed through the [Anthropic Console](https://console.anthropic.com). To rotate the key:

1. Generate a new key in the Anthropic Console
2. Update the Worker secret: `wrangler secret put ANTHROPIC_API_KEY`
3. Delete the old key from the Console
4. No changes to `index.html` are needed

## 9. Deployment guide

### First-time setup

**Step 1: Deploy the Cloudflare Worker**

1. Create a Cloudflare account (or use an existing one)
2. Install Wrangler: `npm install -g wrangler`
3. Log in: `wrangler login`
4. Create a new Worker project and paste the Worker code from [Section 7](#7-the-cloudflare-worker-api-proxy)
5. Add the API key as a secret: `wrangler secret put ANTHROPIC_API_KEY`
6. Deploy: `wrangler deploy`
7. Note the Worker URL (e.g. `https://cadi-search-proxy.your-name.workers.dev`)

**Step 2: Configure index.html**

Open `index.html` and update the two constants at the top of the script:

```js
const PROXY_URL = "https://cadi-search-proxy.your-name.workers.dev";
const GITHUB_RAW_INDEX_URL = "https://raw.githubusercontent.com/YOUR-ORG/YOUR-REPO/main/search-index.json";
```

**Step 3: Run the initial crawl**

Either run the crawler locally:

```bash
python scripts/crawl.py --url https://cadi.port.ac.uk --output search-index.json
```

Or trigger the GitHub Actions workflow manually (see [Section 6](#6-github-actions-automated-crawling)).

**Step 4: Commit and push**

Commit `index.html` and `search-index.json` to the repository and push.

**Step 5: Deploy the HTML file**

Deploy `index.html` to wherever it will be served. Options include:

- **GitHub Pages** — enable Pages in the repository settings, set the source to the `main` branch and root directory
- **Netlify / Vercel** — drag and drop the file or connect the repository
- **Any static host** — the file is entirely self-contained and has no server-side dependencies

### Updating after initial deployment

The knowledge index updates automatically every Sunday. To update the UI, assistant behaviour, or configuration:

1. Edit `index.html`
2. Commit and push
3. The change is live immediately — no build step needed

## 10. Branding and design

The interface follows the University of Portsmouth brand guidelines (September 2024 edition) and is consistent with the search interface.

### Colour palette

All colours are defined as CSS custom properties on `:root` in the `<style>` block, and as a JavaScript constants object (`C`) in the script. Both must be updated if colours change.

| Token | Name | Hex |
|---|---|---|
| `--primary-dark` | Dark Purple | `#3C023C` |
| `--primary` | Light Purple | `#621360` |
| `--secondary-dark` | Dark Blue | `#0078B4` |
| `--secondary` | Light Blue | `#00A0FF` |
| `--black` | Black | `#000000` |
| `--dark-grey` | Dark Grey | `#505457` |
| `--mid-grey` | Mid Grey | `#ABAAAA` |
| `--light-grey` | Light Grey | `#D1D1D1` |
| `--lighter-grey` | Lighter Grey | `#F7F7F7` |
| `--off-white` | Off White | `#FAFAFA` |
| `--white` | White | `#FFFFFF` |

The page background is a gradient from Dark Purple → Light Purple → Dark Purple. Light Blue (`#00A0FF`) is used as the primary accent colour throughout (send button, input focus, assistant message border, step indicators). All interactive elements use 0 border-radius — no rounded corners anywhere in the interface.

### Typography

Per the University of Portsmouth brand guidelines, two Google Fonts are used:

- **Encode Sans Expanded** — the CADI logomark, headings, and message sender labels. Bold (700) and Extra Bold (800) weights.
- **Open Sans** — all body copy, chat messages, input fields, and suggestion chips.

The primary brand font (Aero) is a licensed typeface not available on Google Fonts and is not used in this web interface.

### Chat message design

- **User messages** — displayed with a "You" avatar, dark semi-transparent background, subtle white border
- **Assistant messages** — displayed with a "C" avatar in the secondary blue gradient, dark background with a left-side blue accent border
- **Thinking indicator** — shown while Claude is processing, with animated step labels (Reading knowledge base → Understanding your question → Composing response) that appear sequentially with a spinning indicator on the current step

## 11. Maintaining and extending the project

### Updating the example prompts

Edit the `EXAMPLE_PROMPTS` array in `index.html`. These should reflect the most common questions staff ask. Review GA search data and any analytics on the assistant periodically to inform this.

```js
const EXAMPLE_PROMPTS = [
  "How do I get AdvanceHE Fellowship?",
  "What CPD sessions are coming up?",
  ...
];
```

### Changing the assistant's behaviour or tone

Edit the `buildSystemPrompt` function in `index.html`. The system prompt controls:

- How Claude introduces itself and what it says it can help with
- The topics it is configured to discuss
- Response length and format (currently 2–4 short paragraphs)
- Whether and how it links to pages
- How it handles questions it cannot fully answer

### Adjusting relevance scoring

The `scorePages` function controls which pages are passed to Claude. You can adjust:

- **`topN`** (default: 20) — how many pages are passed per request. Increase for more context; decrease to reduce token usage further.
- **Point values** — the weights assigned to title, tag, excerpt, and content matches. Increase title weight if title-based relevance is most important for your site.
- **Fuzzy match threshold** — currently allows 1 character difference for words of 5+ characters. Increase for more aggressive typo tolerance.

### Adjusting conversation context depth

`buildSystemPrompt` uses the last 3 user messages for scoring context. To change this:

```js
const recentContext = priorMessages
  .filter(m => m.role === "user")
  .slice(-3)   // ← change this number
  ...
```

Increase for longer conversational threads; decrease if users tend to change topic frequently.

### Changing the AI model

The model is set in the `send` function:

```js
model: "claude-sonnet-4-20250514",
```

Check the [Anthropic documentation](https://docs.anthropic.com) for the latest model names. When upgrading, test conversational quality before deploying — newer models may respond differently in tone or format.

### Adjusting how much of each page is sent to Claude

In `buildSystemPrompt`, the content slice controls how many characters of each page's `content` field are included:

```js
DETAIL: ${(p.content || "").slice(0, 500)}
```

Increase this for richer answers on complex topics; decrease if token usage becomes a concern.

### Adjusting the crawler

See [Section 4](#4-the-site-crawler-scriptscrawlpy) for details on which constants to change if the Drupal site structure changes.

### Changing the crawl frequency

Edit the cron expression in `.github/workflows/crawl_site.yml`:

```yaml
- cron: '0 2 * * 0'   # Current: weekly, Sunday 2am UTC
```

Use [crontab.guru](https://crontab.guru) to generate alternative expressions.

### Reusing this project for a different site

The scoring logic (`getCorePages`, `scorePages`, `buildSystemPrompt`) contains no CADI-specific assumptions:

- `getCorePages` detects homepage, contact, and about pages by URL pattern — no hardcoded IDs
- `scorePages` works against any `search-index.json` produced by the crawler
- The system prompt persona and topic list in `buildSystemPrompt` will need updating for a different department

To reuse for another UoP department: update `PROXY_URL`, `GITHUB_RAW_INDEX_URL`, `FALLBACK_INDEX`, `EXAMPLE_PROMPTS`, and the persona text in `buildSystemPrompt`.

## 12. Troubleshooting

**"I'm having trouble connecting right now" error message**

The Cloudflare Worker is unreachable or returning an error. Check:
1. The Worker is deployed and the `PROXY_URL` in `index.html` is correct
2. The `ANTHROPIC_API_KEY` secret is set on the Worker
3. The Anthropic API key is valid and has available credits in the [Anthropic Console](https://console.anthropic.com)
4. Open browser DevTools → Network tab → look at the failed POST request for the raw error message

**The assistant gives outdated or incomplete answers**

The knowledge index is refreshed weekly. Either wait for the next Sunday crawl, or trigger a manual run via GitHub Actions (see [Section 6](#6-github-actions-automated-crawling)). For pages added or significantly updated mid-week, a manual crawl is the fastest fix.

**The assistant says it can't find information but the page exists on the site**

The page may not have scored highly enough against the query to be included in the top 20 sent to Claude. Check:
1. Open `search-index.json` and find the page — confirm it has a meaningful `title`, `tags`, and `content` field
2. If `content` is thin or contains navigation boilerplate rather than actual page text, update `CONTENT_SELECTORS` or `NOISE_TAGS` in `crawl.py` and re-run the crawl
3. Adding relevant terms to the page's `tags` in the index (by improving the crawler's tag extraction) will improve its score for related queries

**The assistant answers confidently but with wrong information**

Check the `content` field in `search-index.json` for the relevant pages. If the crawler is extracting navigation text or boilerplate rather than actual page content, update `CONTENT_SELECTORS` or `NOISE_TAGS` in `crawl.py` and re-run the crawl.

**Follow-up questions produce unrelated responses**

The assistant scores the index against the last 3 user messages combined. If a conversation goes longer than 3 turns and later messages are very different in topic, earlier context may be lost. This is expected behaviour. Users can click **Clear** to start a fresh conversation on a new topic.

**The GitHub Actions crawler fails with "No pages indexed"**

The crawler may be blocked, the site may be temporarily down, or a Drupal theme change has broken content extraction. Check the Actions run log. Debug locally:

```bash
python scripts/crawl.py --url https://cadi.port.ac.uk --max-pages 10
```

**CORS error when fetching the GitHub index**

GitHub's raw content endpoint (`raw.githubusercontent.com`) returns permissive CORS headers for public repositories. If the repository is private, the browser cannot fetch the file directly. Either make the repository public or host `search-index.json` on a server that sets `Access-Control-Allow-Origin: *`.

**Responses are slow**

Each message scores 180+ pages locally (fast, in-browser) and then sends ~20 pages to Claude. Response time is primarily Claude API latency. If responses are consistently slow, check the [Anthropic status page](https://status.anthropic.com). Reducing `topN` in `scorePages` (e.g. from 20 to 12) will reduce payload size slightly but is unlikely to make a meaningful difference to latency.

**The conversation goes off-topic**

Edit the `buildSystemPrompt` function to more tightly scope the topics Claude will discuss. Adding an explicit instruction such as "If asked about topics unrelated to CADI or academic development at the University of Portsmouth, politely redirect the conversation" will help.
